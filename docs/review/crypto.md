## Checked and sound

- vault.js: PBKDF2-SHA256 at 600000 iterations, 16-byte random salt, AES-GCM 256, non-extractable base and derived keys, a fresh 12-byte IV per encrypt, strict base64, IV length check, one generic error on any failure. `parseEnvelope` pins v, name, hash and iter, so a planted envelope cannot lower the KDF cost.
- The outer and inner `_meta` binding (rev, updatedAt, deviceId) is checked with types and bounds. The rollback check `rr < remoteRev` holds across file replacement, because rev is checked independently of file id. Remote revs strictly increase under normal flows (`max(..)+1`, and conflict-local uses `rr+1`).
- `adoptEnvelope` persists only whitelisted envelope fields. A restore never brings sync bookkeeping, and an adopt overwrites it with the local client id.
- Older schemas: v0.11 rejects schema 11, so it cannot adopt or upload over it, because `run` throws before any write. `droppedData` covers every schema 11 addition and a missing private vault. A sync download and a restore both need the explicit tick, and `replaceState` re-checks against the live state.
- priv.js: `cleanBlob` uses a strict whitelist with fixed iter, salt, IV and ct sizes and allowlisted marks. Inner rev is bound to outer rev. `checkInner` blocks unknown keys and `__proto__`. Close bumps `gen` and scrubs inner records that views share. It closes on visibility hidden, lock, adopt, restore and either passphrase change. Writes re-check `key !== k` after each await, and the SEC-63 and SEC-64 paths hold.
- store.js races: `commit` and `replaceState` re-check key and state identity, and the serial queue orders exportEnvelope, adopt and changePassphrase. `lock()` empties the live state object. Locking from the UI also drops the Google token (app.js:265) and closes dialogs, which holds the sync decision context.
- OAuth: a 128-bit state nonce, the only sessionStorage item, consumed once and compared in constant time. The fragment is stripped before parsing, even without storage. The token format and `bearer` type are checked, scope checked when present, and TTL clamped. The token lives in memory only and appears in no error, state or log. `drive.appdata` scope only, `include_granted_scopes=false`, https or localhost only.
- Drive requests: `credentials:'omit'`, `redirect:'error'`, `no-store`, `no-referrer`, a 30 s abort, a 64 MB cap enforced on Content-Length, metadata size and a streamed byte count. Error text is fixed. File ids are regex-checked before they go into URLs. The version is re-read before PATCH, plus If-Match.
- Build: dist/lifeos.html and both `_headers` files are byte-identical to a fresh `buildAll`. The CSP hashes match the single inline script and style. There are no inline handlers or `style=` attributes, inlining uses a function replacer (no `$&` expansion), and `</style` is CSS-escaped. The CSP has default-src 'none', base-uri 'none', form-action 'none', and frame-ancestors 'none' in the header.

## Could not verify

- Whether Drive v3 honours `If-Match` on `upload/drive/v3/files/{id}?uploadType=media`, and whether the ETag from the `alt=media` GET is the one it compares. If it ignores the header, only the non-atomic version re-read protects against lost updates. If it compares a different ETag, every upload after a download may fail with 412.
- Whether Drive ever answers `alt=media` with a redirect (that would break sync under `redirect:'error'`).
- Whether the conflict path's "save losing copy" download (`saveBackup` resolves at once, after several awaits) survives browsers that block a programmatic download once the user gesture has expired (iOS Safari, installed PWAs). If it is blocked, the conflict resolution proceeds without the backup.
- Cloudflare Pages settings: which directory is published, whether pretty URLs (`/dist/lifeos` without `.html`) skip the `/*.html` Cache-Control rule, and that `_headers` is in the output root.
- JS cannot zero memory: passphrase strings, the decrypted remote state in a pending sync decision and `getWellbeing()` clones live until GC.

## v1.8.0 key layout (envelope v2, audited 22 Nov 2026)

The v0.12.0 notes above describe the v1 layout (the state sealed directly under the passphrase key). Since v1.8.0:

- Main vault file: `{v:1, kdf, iv, ct, fmt:2, wraps:[{kind, kdf, iv, wk}], data:{iv, ct}, rev, updatedAt, deviceId}`. `data` is the state (with `_meta`) under a random AES-GCM 256 data key. Each wrap is the data key wrapped with AES-GCM (AAD "lifeos-wrap-v2:" plus kind) under a key derived by PBKDF2-SHA256, 600,000 iterations, from the passphrase or the recovery key, with its own 16-byte salt. At most one wrap per kind; the passphrase wrap is required. `kdf`/`iv`/`ct` is a stub `{schema:20, newerFormat:true, _meta}` under the passphrase key-encryption key, so v1.7.0 refuses the file with its newer-version message; it is checked when a passphrase opens the file.
- Private vault blob: `{v:2, wraps, iv, ct, rev, marks}` with its own data key and wraps (private passphrase, private recovery key). Private archive boxes carry the private wraps in force when sealed.
- Backups and archive files: a fresh data key under their own passphrase, plus the main recovery wrap when the key is typed at export (required while a key is on). Drive copies are the stored file.
- Rotation: every change of the wrap set makes a new data key and fresh salts. Data keys are non-extractable after unwrap. Parsing is strict (unknown fields refused, sizes checked). v1 files open and are written as v2 on the next save.
- Sync compares the passphrase wrap salt as the key identity (`saltId`); a v1 upgrade carries the sync record forward (SEC-127).
- Findings and proofs: docs/SECURITY.md "v1.8.0 audit" (SEC-127 to SEC-133), test/v180.test.mjs, test/v180-audit.test.mjs.

## v2.0.0 threat model change (NAS sync, audited 22 Nov 2026)
- A new place holds ciphertext: the NAS service keeps the last 30 vault envelopes and the archive files. It never receives a passphrase, recovery key, data key or plaintext; it reads only outer fields. Anyone who takes the dataset gets what a Drive copy gives: offline guessing at the PBKDF2 cost.
- A compromised or restored NAS can serve an older genuine copy. The envelope revision (bound to the inner one) and this device's NAS bookkeeping refuse it as a rollback; it is never adopted, and the owner may replace it after saving it to a file (SEC-134). It cannot forge a newer copy without a key.
- The device token is a bearer secret inside the encrypted state and inside every sealed copy; the service stores only its SHA-256. A stolen token lets its holder read and replace ciphertext on the NAS (on the tailnet only), which the rollback and conflict rules on each device then catch.
